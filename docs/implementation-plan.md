# План реализации OSNOVA

Статус: черновик для проверки архитектором. Реализация начнётся после
согласования. Приоритеты: P0 (запуск), P1 (рост SEO/контент), P2 (удобство,
не обязательное для запуска).

Каждая задача содержит: приоритет, файлы/модули, зависимости, критерии приёмки,
способ проверки. Обозначения: **D#** — блокирующее решение/вопрос (см. §8).

---

## 0. Блокирующие решения (нужны до старта P0)

См. §8. Ключевые: D1 (бэкап/remote), D2 (судьба чистки комментариев),
D3 (конвенция base-URL API), D4 (способ уведомления преподавателя),
D5 (продакшн-домен), D6 (текст политики ПД).

## 1. P0 — сохранность, интеграция API, рабочие заявки, юридический минимум, индексация

### G-1. Бэкап и фиксация в git  *(блокер, делается первым)*
- **Приоритет:** P0 (блокер). **Зависимости:** D1, D2.
- **Файлы:** весь репозиторий; `.gitignore` (корень/`frontend`/`backend`).
- **Шаги:**
  1. Полный снимок: `cp -a . ../osnova.backup-$(date +%F)` (плюс `git bundle create`).
  2. `git add backend && git commit` — backend отдельно.
  3. `git add frontend/src/lib/theme.ts frontend/src/components/ui/theme-toggle.tsx
     frontend/src/app/globals.css frontend/src/app/layout.tsx
     frontend/src/components/layout/mobile-nav.tsx` — тёмная тема.
  4. `git add frontend/src/features/home/components/about-illustration.tsx` — иллюстрация.
  5. `git add docs README.md` — документация.
  6. 53 файла с удалением комментариев: отдельный `chore:` или откат (по D2).
  7. Добавить remote (по D1).
- **Приёмка:** `git status` чистый; история = логичные атомарные коммиты; есть
  off-machine копия.
- **Проверка:** `git log --oneline`, `git status --short`, `git remote -v`.

### A-1. Единый способ формирования `/api/v1`
- **Приоритет:** P0. **Зависимости:** D3.
- **Файлы:** `frontend/src/lib/api/config.ts` (добавить `API_VERSION = "/api/v1"`),
  `frontend/src/lib/api/server.ts`, `frontend/src/lib/api/client.ts`
  (строить `joinUrl(base, API_VERSION, path)`), обновить `.env.example` и
  `next-steps.md` (base = origin).
- **Приёмка:** `API_BASE_URL`/`NEXT_PUBLIC_API_BASE_URL` = `http://localhost:8000`;
  запросы уходят на `/api/v1/...`; `/api/health` не ломается.
- **Проверка:** `pnpm typecheck`; ручной запрос к каталогу при поднятом бэке
  (остановить бэк → каталог показывает `StateMessage`, а не фикстуры).

### A-2. Подключить проверку ответа к API
- **Приоритет:** P0. **Зависимости:** A-1.
- **Файлы:** `frontend/src/features/tasks/api.ts` (+`checkTaskAnswer`),
  `frontend/src/features/tasks/components/answer-form.tsx` (вызов API при
  `isPublicApiConfigured()`, иначе локальный fallback).
- **Приёмка:** при заданном `NEXT_PUBLIC_API_BASE_URL` проверка идёт через
  `POST /tasks/{id}/check`; попытка пишется в `solution_attempts`; у
  залогиненного — в `user_progress`; без API — прежний локальный режим.
- **Проверка:** `pnpm test` (unit `answer-form.test.tsx`), ручная проверка +
  `GET /progress` под залогиненным пользователем.

### A-3. Согласовать CORS и cookie для продакшена
- **Приоритет:** P0. **Зависимости:** D5.
- **Файлы:** `backend/app/main.py` (сузить `allow_methods=["GET","POST"]`,
  `allow_headers=["Content-Type","Accept"]`; добавить production origin),
  `backend/app/core/config.py` (значения по умолчанию).
- **Приёмка:** браузерный `POST /tutor-leads` и `POST /tasks/{id}/check` проходят
  с продакшн-origin; куки `site_bank_session` работают.
- **Проверка:** ручной e2e с двух origins; `curl -i` на preflight.

### L-1. Уведомление преподавателя о заявке
- **Приоритет:** P0. **Зависимости:** D4.
- **Файлы:** `backend/app/domains/leads/service.py` (в `create_lead` после
  `flush` — отправить уведомление, обёрнутое в try/except),
  `backend/app/core/config.py` (+`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`
  и/или SMTP-переменные), новый `backend/app/domains/leads/notify.py`.
- **Приёмка:** успешная заявка доходит до преподавателя (Telegram/SMTP); сбой

- **Проверка:** ручная подача формы → сообщение получено; временно «сломать»
  токен → заявка сохранена, HTTP 201, лог содержит ошибку.

## 2. P1 — SEO-страницы и качественное расширение банка

### P-1. Экзаменационные гайды (4 страницы)
- **Приоритет:** P1. **Зависимости:** S-2, реальный контент.
- **Файлы:** `frontend/src/app/(public)/ege-matematika/page.tsx`,

  `features/exam-guide/` + 4 тонкие страницы), `features/topics/content.ts`

### P-2. Расширение банка задач/статей
- **Приоритет:** P1. **Зависимости:** C-1.
- **Файлы:** данные через `scripts/seed.py` (или будущий импорт), при
  необходимости — типизация блоков в `tasks/schemas.py`/`articles/schemas.py`.

  `dynamicParams` при необходимости).
- **Приёмка:** новые задачи/статьи индексируются без пересборки; неизвестные id →
  404.
- **Проверка:** `pnpm build`; e2e `task-page.spec.ts` (404 для несуществующих).

## 5. Риски и обратная совместимость
- Фикстуры остаются fallback-режимом при пустом `API_BASE_URL` — P0 не должен их
  сломать (e2e `seo.spec.ts`/`task-page.spec.ts` зелёные в обоих режимах).
- `Article.subject` может быть `null` из API — при A-2/P-1 предусмотреть защиту UI.
- Уведомление (L-1) не должно влиять на транзакцию заявки.
- Любые новые таблицы — только с миграцией Alembic и обоснованием (P0/P1 без них).

## 8. Блокирующие вопросы

1. **D1 — Бэкап/remote.** Внешней копии нет (`git remote -v` пуст). Куда
   публиковать (GitHub/GitLab/иной) и заводить ли CI сейчас? Без этого сохранность
   не гарантирована.
2. **D2 — Чистка комментариев.** 53 файла с удалёнными JSDoc. Это осознанное
   решение (оставить как отдельный `chore:`-коммит) или артефакт, который нужно
   откатить?
3. **D3 — Конвенция base-URL API.** Принять «base = origin, версия в коде
   (`/api/v1`)» (рекомендую) или «base включает `/api/v1`, код не меняется»?
4. **D4 — Уведомление о заявке.** Telegram-бот (токен + chat_id) или SMTP?
   Нужны реальные учётные данные.
5. **D5 — Продакшн-домен.** Домен сайта и домен/поддомен API — от них зависят
   canonical, sitemap, CORS, `COOKIE_DOMAIN`/`SameSite`.
6. **D6 — Политика ПД.** Кто готовит юридический текст `/privacy` (владелец/юрист),
   кто является оператором персональных данных?
7. **D7 — Роль администратора.** Подтвердить, что администратор создаётся только
   CLI-скриптом (без публичного эндпоинта регистрации админа).

После ответов на D1–D7 план считается согласованным, и можно начинать реализацию
с шага G-1.
