# Контракт интерактивного контента статей

Дата: 2026-10-17. Статус: проект контракта (документация). Ничего из описанного
не реализовано: схема БД, существующие модели и API не менялись.

Этот документ определяет единый формат контента интерактивной образовательной
статьи, который будет храниться в PostgreSQL JSONB, валидироваться на backend,
передаваться типизированным API и рендериться на frontend.

---

## 1. Цели и принципы

Формат должен:

1. храниться в JSONB (PostgreSQL) без схемы на уровне БД — схему задаёт приложение;
2. валидироваться на backend (Pydantic, дискриминированный union — как уже
   сделано для задач в `backend/app/domains/tasks/schemas.py`);
3. передаваться типизированным API (Pydantic → JSON → TypeScript);
4. рендериться на frontend безопасно (без сырого HTML, без `eval`);
5. поддерживать версионирование схемы;
6. расширяться новыми типами блоков без изменения общей архитектуры.

**Принципы безопасности:** контент декларативен и не содержит исполняемого кода
(нет JS, Python, `eval`, произвольного HTML). Всё, что приходит из контента,
экранируется при рендере, кроме явно разрешённого безопасного подмножества.

---

## 2. Формат документа (верхний уровень)

Контент статьи — это один JSON-объект, хранящийся в JSONB. SEO-метаданные
(`title`, `description`, `exam`, `reading_minutes`, `subject_id`,
`published_on`, `updated_on`) **не дублируются** в документе — они остаются
колонками таблицы `articles` (`backend/app/domains/articles/models.py`), где уже
живут сегодня. Документ содержит только тело статьи.

```json
{
  "version": 2,
  "blocks": [ { "id": "...", "type": "...", "data": { } } ]
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `version` | integer | да | Версия схемы контента. Текущая — `2` (см. §6). |
| `blocks` | array | да | Упорядоченная последовательность блоков (может быть пустой). |

**Блок** — единая форма для всех типов:

```json
{ "id": "b1", "type": "rich_text", "data": { } }
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Стабильный идентификатор блока. |
| `type` | string | да | Дискриминатор типа (snake_case). |
| `data` | object | да | Типизированные данные блока (может быть `{}`). |

**Правила идентификаторов блоков:**

- уникальны в пределах документа (валидатор отклоняет дубликаты);
- стабильны: однажды опубликованный `id` не меняется при правках и перестановке
  блоков (на него ссылаются якоря, аналитика и, в будущем, прогресс упражнений);
- формат: `^[a-zA-Z0-9_-]{1,64}$`.

---

## 3. Общие правила блоков

- Каждый блок — `{ id, type, data }`; поле `data` типизировано и всегда присутствует.
- **Неизвестный `type`**: при чтении/рендере такой блок **пропускается**, а не
  роняет страницу. Валидатор на запись отклоняет неизвестные типы.
- **Лишние поля** в `data` (не из схемы) — игнорируются (forward compatibility).
- **Отсутствующие обязательные поля** в `data` — ошибка валидации.
- Порядок блоков в `blocks` задаёт порядок отображения.

---

## 4. Типы блоков

Дискриминатор `type` — snake_case. Внутри `data` ключи — snake_case (соглашение:
контент в JSONB хранится в snake_case; wire-формат верхнего уровня `ArticleRead`
по-прежнему использует camelCase-алиасы — см. §9).

### 4.1 `rich_text` — абзацы, заголовки, списки, ссылки, выделение

```json
{
  "id": "rt-1",
  "type": "rich_text",
  "data": {
    "kind": "paragraph",
    "children": [ { "type": "text", "text": "Обычный текст" } ]
  }
}
```

`data`:

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `kind` | `"paragraph" \| "heading" \| "list"` | да | Вид блока. |
| `children` | InlineNode[] | для paragraph/heading | Инлайновые узлы. |
| `level` | `2 \| 3` | для heading | Уровень заголовка (h2/h3; h1 занят заголовком страницы). |
| `ordered` | boolean | list (default `false`) | Нумерованный/маркированный список. |
| `items` | InlineNode[][] | для list | Элементы списка; каждый — последовательность инлайновых узлов. |

Правила: у `paragraph` обязателен непустой `children`, запрещены `level/ordered/items`;
у `heading` — `children` + `level ∈ {2,3}`; у `list` — непустой `items`, каждый
элемент непуст, `children/level` запрещены.

### Инлайновые узлы (InlineNode)

Дискриминированный union по `type` (тот же механизм, что и для блоков):

| `type` | Поля | Назначение |
| --- | --- | --- |
| `text` | `text: string` | Обычный текст (экранируется). |
| `strong` | `children: InlineNode[]` | Жирное выделение. |
| `em` | `children: InlineNode[]` | Курсив. |
| `code` | `text: string` | Инлайновый код (информатика). |
| `link` | `href: string`, `children: InlineNode[]` | Ссылка. |
| `math` | `tex: string` | Инлайновая формула LaTeX. |
| `br` | — | Перенос строки. |

`code` — опционален (включён, т.к. информатика — профильный предмет); при
необходимости может быть исключён без ломки формата.

**Правила безопасного преобразования в HTML (§8)** обязательны для `link`.

### 4.2 `math` — формула LaTeX

```json
{
  "id": "math-1",
  "type": "math",
  "data": { "tex": "\\frac{a}{b}", "display": true, "caption": "Дробь" }
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `tex` | string (≤4096) | да | Исходный LaTeX. |
| `display` | boolean | нет (default `true`) | Блочная (`true`) или инлайновая (`false`) формула. |
| `caption` | string | нет | Подпись/нумерация. |

Хранится **только исходный LaTeX**, рендер-HTML не является источником истины
(генерируется KaTeX на сервере — `frontend/src/components/ui/math.tsx`).

### 4.3 `interactive_graph` — интерактивный график

```json
{
  "id": "graph-1",
  "type": "interactive_graph",
  "data": {
    "engine": "svg",
    "expressions": [
      { "id": "f", "expr": "a*x^2 + b", "label": "f(x)", "color": "#1f6feb" }
    ],
    "parameters": [
      { "id": "a", "label": "a", "min": -3, "max": 3, "step": 0.5, "default": 1 },
      { "id": "b", "label": "b", "min": -5, "max": 5, "step": 0.5, "default": 0 }
    ],
    "viewport": { "x_min": -5, "x_max": 5, "y_min": -5, "y_max": 5 },
    "interactions": ["pan", "zoom", "trace"]
  }
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `engine` | `"svg"` | да | Единственный разрешённый движок (соответствует самописному SVG-подходу `features/home/components/derivative-graph.tsx`). |
| `expressions` | Expression[] | да (1…N) | Кривые/функции. |
| `parameters` | Parameter[] | нет | Интерактивные параметры (слайдеры). |
| `viewport` | Viewport | нет | Начальная видимая область. |
| `interactions` | enum[] | нет | Разрешённые взаимодействия. |

**Expression**: `{ id, expr, label?, color? }` — `id` уникален среди expressions;
`expr` — строка ограниченной математической грамматики (см. §9 без eval);
`color` — hex (`#rrggbb`).

**Parameter**: `{ id, label, min, max, step, default }` — `id` уникален среди
parameters; `min ≤ default ≤ max`; `step > 0`; `id` может использоваться в `expr`
как переменная. Начальные значения берутся из `default`.

**Viewport**: `{ x_min, x_max, y_min, y_max }` — числа, `min < max`.

**Interactions** — подмножество `["pan", "zoom", "trace"]`; `trace` — перемещение
точки по кривой (как `range input` в `derivative-graph`).

**Грамматика `expr` (строгая, без кода):**

- переменные: `x` и идентификаторы из `parameters`;
- числа и литералы `pi`, `e`;
- операторы `+ - * / ^ ( )`; унарный минус;
- функции (белый список): `sin cos tan asin acos atan exp ln log2 log10 sqrt abs`;
- запрещено: `=` (присваивание), `;`, строки, вызов произвольных функций,
  доступ к атрибутам/индексам, любые последовательности вне белого списка.

Выражения вычисляются на клиенте только встроенным парсером строгой грамматики
(без `eval`/`Function`); backend валидирует ту же грамматику. Это позволяет
менять параметры без запросов к API. Произвольный JS/Python/`eval` запрещён на
всех уровнях.

### 4.4 `single_choice` — вопрос с вариантами ответа

```json
{
  "id": "ex-1",
  "type": "single_choice",
  "data": {
    "prompt": [ { "type": "text", "text": "Чему равна производная x^2?" } ],
    "options": [
      { "id": "o1", "label": [ { "type": "text", "text": "2x" } ] },
      { "id": "o2", "label": [ { "type": "text", "text": "x" } ] }
    ],
    "correct_option_id": "o1",
    "explanation": [ { "type": "text", "text": "По правилу степени." } ],
    "points": 1
  }
}
```

| Поле | Тип | Обязательно | Публичное? |
| --- | --- | --- | --- |
| `prompt` | InlineNode[] | да | да |
| `options` | Option[] (2…N, id уникальны) | да | да (только `id`+`label`) |
| `correct_option_id` | string | да | **нет** (серверное) |
| `explanation` | InlineNode[] | нет | раскрывается после ответа |
| `points` | number | нет (default `1`) | да |

`correct_option_id` обязан совпадать с одним из `options[].id`.

### 4.5 `numeric_input` — числовой ответ

```json
{
  "id": "ex-2",
  "type": "numeric_input",
  "data": {
    "prompt": [ { "type": "text", "text": "Решите: 2 + 2 =" } ],
    "correct_value": 4,
    "tolerance": 0,
    "unit": "",
    "explanation": [ { "type": "text", "text": "2 + 2 = 4." } ],
    "points": 1
  }
}
```

| Поле | Тип | Обязательно | Публичное? |
| --- | --- | --- | --- |
| `prompt` | InlineNode[] | да | да |
| `correct_value` | number | да | **нет** (серверное) |
| `tolerance` | number | нет (default `1e-9`) | **нет** (серверное) |
| `unit` | string | нет | да |
| `explanation` | InlineNode[] | нет | раскрывается после ответа |
| `points` | number | нет (default `1`) | да |

Проверка: `|answer − correct_value| ≤ tolerance` (абсолютная). Правило сравнения —
серверное, не публикуется.

### 4.6 `step_solution` — последовательность шагов решения

```json
{
  "id": "sol-1",
  "type": "step_solution",
  "data": {
    "steps": [
      { "id": "s1", "note": [ { "type": "text", "text": "Применяем правило степени" } ],
        "math": { "tex": "(x^n)' = n x^{n-1}", "display": true } },
      { "id": "s2", "note": [ { "type": "text", "text": "Подставляем n = 2" } ] }
    ]
  }
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `steps` | Step[] (1…N) | да | Шаги в порядке следования. |

**Step**: `{ id, note: InlineNode[], math?: { tex, display? } }` — `id` уникален
среди шагов; `math` опционален (шаг может быть только текстовым). Соответствует
существующему `SolutionStep{note, tex}` (`tasks/schemas.py:47-49`), расширенному
до rich text + необязательная формула.

### 4.7 `hint` — подсказка

```json
{
  "id": "hint-1",
  "type": "hint",
  "data": {
    "title": "Подсказка",
    "body": [ { "type": "text", "text": "Вспомните определение логарифма." } ]
  }
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `title` | string | нет (default «Подсказка») | Заголовок. |
| `body` | InlineNode[] | да | Содержимое подсказки. |

Рендерится как свёрнутый блок (раскрывается по клику). Несколько подсказок —

```json
{
```

```json
  "data": {
    "src": "/media/grafiki/tangent.png",
    "alt": "Касательная к графику функции",
```

## 5. Разделение публичных и серверных данных

| Блок | Публичные поля | Серверные поля (не покидают backend) |
| --- | --- | --- |
| `single_choice` | `prompt`, `options[].id/label`, `points` | `correct_option_id` |
| `numeric_input` | `prompt`, `unit`, `points` | `correct_value`, `tolerance` |
| `step_solution` | `steps` (note, math) | — |
| `hint` | `title`, `body` | — |
| остальные | все | — |

**Правила:**

- Публичный API статей (`GET /articles`, `GET /articles/{slug}`) всегда отдаёт
  **публичную проекцию** упражнений: поля `correct_option_id`, `correct_value`,
  `tolerance` **вырезаются** перед сериализацией (иначе ответ утечёт в SSR-HTML —
  тот же риск, что отмечен в аудите для задач, §9.4).
- `explanation` **не входит в публичную выдачу статьи**: он возвращается только
  эндпоинтом проверки ответа и только при верном ответе (политика UI).
- Проверка ответа выполняется **только сервером** по серверным полям; клиент
  получает результат в уже существующей форме `{isCorrect, checkedAt, explanation?}`
  (`solutions/schemas.py::AnswerCheckResponse`).

## 6. Версионирование схемы

- `version` в документе — целое число. Текущее значение **2** (v1 — исторический
  формат `articles.blocks` из пяти блоков `paragraph/heading/list/formula/quote`).
- **Minor/аддитивное** изменение (новый тип блока, новое необязательное поле) —
  обратно совместимо; `version` можно не менять или поднять минорную часть.
- **Major/ломающее** изменение (удаление/переименование поля, смена семантики) —
  новый major `version`; старый контент продолжает читаться по своей версии.
- **Чтение неизвестной версии:** если `version` новее поддерживаемой, backend не
  падает: отдаёт статью с пустым/частичным контентом и предупреждением; страница
  рендерит то, что понимает.
- **Неизвестный тип блока** при чтении — блок пропускается (логируется warning),
  остальные блоки рендерятся; падение всей страницы не допускается.
- **Backfill v1→v2** вынесен за рамки контракта (текущие v1-блоки остаются в
  `articles.blocks`; новый контент пишется в новое поле — см. §10).

## 7. Правила валидации

1. **Конверт:** `version` — положительное целое; `blocks` — массив (возможно пустой).
2. **Блок:** `id` соответствует `^[a-zA-Z0-9_-]{1,64}$`; `id` уникальны; `type` —
   из известного набора; `data` — объект.
3. **`data` по типу** — валидация строгой схемой каждого типа (таблицы §4).
4. **Ссылочная целостность внутри документа:** `single_choice.correct_option_id`
   ∈ `options[].id`; `interactive_graph.expressions[].expr` ссылается только на
   объявленные `parameters[].id` или `x`; идентификаторы expressions/parameters/steps
   уникальны в своём контексте.
5. **Запись** (создание/обновление контента): невалидный блок → отклонение с
   указанием блока и причины (конверт ошибок `app/core/exceptions.py`).
6. **Чтение:** невалидный/неизвестный блок в уже сохранённом документе →
   пропуск блока + warning, не падение (устойчивость к частично повреждённым данным).

Реализация — Pydantic: `BaseModel` на каждый блок + `Annotated[... , Field(discriminator="type")]`
+ `TypeAdapter[list[Block]]`, по образцу `tasks/schemas.py:39-44`.

## 8. Rich text → безопасный HTML

Преобразование инлайновых узлов в HTML выполняется на сервере (или в доверенном
рендере) по фиксированным правилам; **сырой HTML из контента не допускается**.

| InlineNode | HTML |
| --- | --- |
| `text` | экранированный текст (`&`, `<`, `>`, `"`, `'`) |
| `strong` | `<strong>…</strong>` |
| `em` | `<em>…</em>` |
| `code` | `<code>…</code>` |
| `link` | `<a href="…" rel="…">…</a>` |
| `math` | KaTeX (server-side `katex.renderToString`) |
| `br` | `<br>` |

**Правила для `link.href`:**

- разрешены только: относительный `/...` (внутренние переходы) и абсолютный
  `https://...`;
- запрещены `javascript:`, `data:`, `vbscript:`, любые иные схемы;
- внешние ссылки получают `rel="noopener noreferrer"` (и `target="_blank"` — по
  решению UI);
- невалидный `href` → узел рендерится как обычный текст.

Инлайновая математика рендерится KaTeX (совместимо с текущим
`frontend/src/components/ui/rich-text.tsx`, который уже парсит `$...$` в KaTeX);
структурированный формат — замена regex-парсинга `$...$`, а не дополнение к нему.

## 9. Соответствие backend ↔ frontend

Имена полей контента в JSONB — snake_case. Верхний уровень `ArticleRead`
(существующий) использует camelCase-алиасы (`readingMinutes`, `isDemo`), как
сейчас; вложенный `content`/блоки передаются **без алиасов** (snake_case),
поэтому frontend-типы блоков используют snake_case имена полей.

| Слой | Backend (Pydantic, будущий `app/domains/articles/schemas.py`) | Frontend (TS, будущий `features/articles/types.ts`) |
| --- | --- | --- |
| документ | `ArticleContent` (`version`, `blocks`) | `ArticleContent` |
| блок | `ArticleBlockV2` = discriminated union | `ArticleBlockV2` = discriminated union |
| rich_text | `RichTextBlock` + `InlineNode` union | `RichTextBlock`, `InlineNode` |
| math | `MathBlock` | `MathBlock` |
| interactive_graph | `InteractiveGraphBlock` (+`GraphExpression`, `GraphParameter`, `GraphViewport`) | `InteractiveGraphBlock` |
| single_choice | `SingleChoiceBlock` (+`ChoiceOption`) | `SingleChoiceBlock` |
| numeric_input | `NumericInputBlock` | `NumericInputBlock` |
| step_solution | `StepSolutionBlock` (+`SolutionStepV2`) | `StepSolutionBlock` |
| hint | `HintBlock` | `HintBlock` |
| callout | `CalloutBlock` | `CalloutBlock` |
| image | `ImageBlock` | `ImageBlock` |
| divider | `DividerBlock` | `DividerBlock` |

Паттерн — 1:1 с существующим: Pydantic `BaseModel` + `TypeAdapter` (как
`tasks/schemas.py`) ↔ TS discriminated union (как `features/articles/types.ts`).
Отдельный union для «публичной проекции» блока (`PublicBlock`) вырезает
серверные поля (§5) на уровне сериализации.

## 10. Упражнения: переиспользование `tasks`/`solutions`/`progress`

Анализ существующих моделей (`backend/app/domains/`):

- `tasks` — банк задач со `statement/answer/steps`, не про статьи.
- `solutions/solution_attempts` — попытки, ключ `task_id`.
- `progress/user_progress` — агрегат, ключ `(user_id, task_id)`.

**Решение (без дублирования):**

1. Упражнение в статье — **самодостаточно** (ответ и правило проверки хранятся в
   `data` блока, серверно). Это не дублирует `tasks`: `tasks` остаётся отдельным
   банком задач, статья лишь встраивает свои упражнения.
2. Опциональное поле блока-упражнения **`task_ref: string | null`** — ссылка на
   существующую задачу (`tasks.id`). Когда `task_ref` задан, проверка ответа и
   запись в `solution_attempts`/`user_progress` переиспользуют существующий путь
   `POST /tasks/{id}/check` **без изменения схемы**.
3. Для автономных упражнений (без `task_ref`) серверная проверка отвечает
   `{isCorrect, ...}`, но **не пишет** прогресс в текущей итерации — обобщение
   `user_progress` на «элементы статей» отложено (нужна миграция; см. §12).

Это буквально соответствует рекомендации аудита (§11.2, вариант (а) как старт).

## 11. Стратегия обработки ошибок

| Сценарий | Поведение |
| --- | --- |
| Невалидный документ при записи | Отклонение (422/400) с `code` и указанием блока. |
| Неизвестный `type` при чтении | Пропуск блока + warning в лог; остальное рендерится. |
| Неизвестная (более новая) `version` | Статья отдаётся с частичным контентом + флаг `degraded`; 500/падение не допускается. |
| Повреждённый `data` отдельного блока | Пропуск блока; остальное рендерится. |
| Ошибка рендера формулы/графика | Блок рендерится как fallback-текст (исходный `tex`/`expr`), без падения. |

API-ошибки — существующий конверт `{"error": {"code","message","details"}}`
(`app/core/exceptions.py`), без изменений.

## 12. Решения, требующие подтверждения

1. **D-1. Хранение контента.** Новое JSONB-поле `articles.content` (v2) рядом с
   существующим `articles.blocks` (v1) — или миграция v1→v2 с заменой. Рекомендация:
   новое поле `content` + `content_version`; v1 остаётся нетронутым.
2. **D-2. Версия схемы в колонке.** Дублировать `version` из JSONB отдельной
   колонкой `articles.content_version` для индексации/фильтрации, или читать только
   из JSONB. Рекомендация: колонка (дешёвый фильтр «какой контент устарел»).
3. **D-3. Прогресс по автономным упражнениям.** Обобщать `user_progress` (миграция)
   или ограничиться `task_ref` (без миграции). Рекомендация: сейчас `task_ref`,
   обобщение — отдельной итерацией.
4. **D-4. `explanation` публичное или серверное.** Решено: не входит в публичную
   выдачу статьи; возвращается только эндпоинтом проверки и только при верном
   ответе.
5. **D-5. Движок графиков.** Решено: встроенный SVG-движок с безопасным парсером
   выражений (без `eval`), без внешних charting-библиотек. Desmos и сторонние
   движки отклонены (API-ключи/лицензии, внешняя сеть, размер бандла). Доступны
   ползунки параметров, trace и кнопки zoom; pan/pinch-жесты не реализованы.
6. **D-6. Изображения.** `src` только `/media/...` + `https://` — подтвердить, что
   медиа-хостинг (`storage_backend`/S3 из `core/config.py`) будет подключён.
7. **D-7. Версия major для нового контента.** Подтвердить `version: 2` (не `1`),
   чтобы не путать с историческим форматом `blocks`.
