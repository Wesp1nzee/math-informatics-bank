# Аудит готовности OSNOVA к публичному запуску

Дата: 2026-10-17. Режим: **только чтение**. Исходники, конфигурация, зависимости
и существующая документация не менялись; коммиты не создавались; деплой не
выполнялся. Единственный созданный файл — этот отчёт.

## Краткий вывод

**С текущими настройками репозитория публичный запуск делать нельзя.**

Технически платформа работает: все обязательные проверки зелёные, а настроенный
production-сценарий (API + реальные env) проходит end-to-end — заявка сохраняется
в БД, проверка ответа пишется в БД, canonical/sitemap используют заданный домен.
Но запуск блокируют три вещи, и все они — конфигурация/контент/юридическая часть,
а не архитектура:

1. **Форма заявки отсутствует в production без env.** Без
   `NEXT_PUBLIC_TUTOR_TELEGRAM`/`NEXT_PUBLIC_TUTOR_EMAIL` и/или
   `NEXT_PUBLIC_API_BASE_URL` компонент `TutorLeadPanel` возвращает `null` в
   production. Заголовочный CTA «Записаться» ведёт на страницу без формы.
2. **`NEXT_PUBLIC_SITE_URL` по умолчанию = `http://localhost:3000`.** Canonical,
   sitemap, robots, OG и JSON-LD указывают на localhost, если переменная не задана
   при сборке.
3. **`/privacy` — проект документа.** Нет реквизитов оператора, финальных сроков
   хранения и юридической проверки (включая необходимость уведомления
   Роскомнадзора). Обрабатывать реальные ПД до этого нельзя.

После заполнения production-env, финализации политики ПД и выбора реального
контента сайт можно запускать. Обязательные до первого запуска исправления — в
разделе «План», п. 1.

Отдельно: **это технический аудит, а не юридическое заключение.** Вопросы
обработки ПД, согласий, cookie и уведомления РКН требуют проверки юристом.

## 2. Проблемы

Формат: **ID · severity · сложность**. Для каждой — что найдено, доказательство,
последствия, как исправить.

### P0 — блокирует публичный запуск

#### P0-1 · P0 · низкая (конфиг) / средняя (guard)
**Форма заявки и личность преподавателя отсутствуют в production без env.**

- **Что найдено:** `TutorLeadPanel` при `!apiConfigured && !telegram && !email`
  в production возвращает `null`. `siteConfig.tutor` берётся из
  `NEXT_PUBLIC_TUTOR_*`; `hasTutorProfile` требует имя+about. В репозитории нет
  `frontend/.env.local`, а `.env.example` содержит пустые значения. Значит, на
  «чистом» деплое нет ни формы, ни имени/фото/описания преподавателя.
- **Доказательство:**
  - `frontend/src/features/tutor-leads/components/tutor-lead-panel.tsx:11-14`
    — `if (process.env.NODE_ENV === "production") return null;`
  - `frontend/src/lib/constants/site.ts:9-14,32-35` — tutor-поля из env,
    `hasTutorProfile` = имя+about.
  - `frontend/.env.example:10-20` — `NEXT_PUBLIC_TUTOR_*` пустые.
  - Реальный production-прогон без env: `[data-lead-form]` = 0 на `/` и
    `/podgotovka`, `#tutor` = 0.
  - E2E `conversion-cta.spec.ts:67` «no service placeholders are shown in
    production» проходит именно потому, что блок просто отсутствует.
- **Последствия:** главная бизнес-цель (заявка) не работает на дефолтном деплое;
  CTA «Записаться» в шапке ведёт на страницу без формы; нет ответа на вопрос
  «кто преподаватель».
- **Исправление:** задать `NEXT_PUBLIC_TUTOR_NAME`,
  `NEXT_PUBLIC_TUTOR_ABOUT`, `NEXT_PUBLIC_TUTOR_TELEGRAM`/`_EMAIL` и
  `NEXT_PUBLIC_API_BASE_URL` при сборке; добавить deploy-guard, который падает
  (или громко предупреждает), если в production не настроен ни один канал заявки;
  при желании — явное состояние «приём заявок временно недоступен» вместо
  молчаливого отсутствия.
- **Сложность:** низкая (конфиг), средняя (guard в CI).

#### P0-2 · P0 · низкая
**`NEXT_PUBLIC_SITE_URL` по умолчанию указывает на localhost.**

- **Что найдено:** при отсутствии переменной `normalizeSiteUrl` возвращает
  `http://localhost:3000`. От этого значения зависят canonical, sitemap, robots,
  OG/Twitter и JSON-LD.
- **Доказательство:**
  - `frontend/src/lib/constants/site.ts:3-4` — `return "http://localhost:3000";`
  - `frontend/.env.example:3` — значение по умолчанию для локальной разработки.
  - Production-прогон без env: canonical `http://localhost:3000`, sitemap
    `host=http://localhost:3000/`, robots `Sitemap: http://localhost:3000/...`.
  - Production-прогон с `NEXT_PUBLIC_SITE_URL=https://example.test`: canonical,
    sitemap и robots корректно используют `https://example.test`.
- **Последствия:** поисковики получают canonical/sitemap на localhost → страницы
  не индексируются или индексируются с чужим canonical; OG-ссылки битые.
- **Исправление:** задать реальный домен при сборке; добавить проверку в CI/сборке,
  запрещающую `localhost` в production-конфигурации.
- **Сложность:** низкая.

#### P0-3 · P0 · высокая (юридическая) / низкая (техническая)
**Политика обработки ПД — черновик без реквизитов оператора.**

- **Что найдено:** страница `/privacy` существует и доступна из чекбокса
  согласия, но содержит заметный блок «Это проект документа…», обобщённого
  оператора («владелец сайта… точные реквизиты указываются перед запуском»), без
  ИНН/адреса, конкретных сроков хранения и порядка удаления.
- **Доказательство:**
  - `frontend/src/app/(public)/privacy/page.tsx` — блок «Это проект документа…».
  - `frontend/src/features/tutor-leads/components/lead-form.tsx:235-240` — ссылка
    на `/privacy` из согласия (работает).
- **Последствия:** обработка реальных ПД (контакт, имя, сообщение) без финальной
  политики и проверки применимых требований (в т.ч. уведомление РКН, если
  применимо) — юридический и репутационный риск. Видимый «черновик» подрывает
  доверие.
- **Исправление:** юридическая проверка; заполнить реквизиты оператора, цели,
  правовые основания, сроки хранения, права субъекта, порядок удаления/отзыва
  согласия; оценить необходимость уведомления РКН; убрать пометку «проект».
  Технически страница уже готова принять финальный текст.
- **Сложность:** высокая (юридическая), низкая (техническая).

#### P0-4 · P0 · средняя
**Production-конфигурация backend не подготовлена; дефолты небезопасны для прода.**

- **Что найдено:** `.env.example` и `config.py` по умолчанию задают `ENV=dev`,
  `DEBUG=true`, `ALLOWED_HOSTS=["*"]`, локальный `DATABASE_URL`, локальные
  `CORS_ORIGINS`, пустой `IP_HASH_SALT`. Локальный `backend/.env` содержит только
  Telegram-ключи (имена; значения не выводились), без `DATABASE_URL`/`ENV`.
  Postgres локально не отвечает. Отдельного production-чеклиста нет.
- **Доказательство:**
  - `backend/app/core/config.py:24-32,55-59` — дефолты.
  - `backend/.env.example:4-9,34-40`.
  - `backend/.env` — только `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`.
  - `pg_isready` → `localhost:5432 - no response`.
- **Последствия:** при деплое «как есть» API не подключится к БД, будет работать
  в debug-режиме, CORS не пропустит реальный домен, cookie не станет `Secure`
  (т.к. `ENV != prod`), IP-хэш будет без соли.
- **Исправление:** production-чеклист и guard: `ENV=prod`, `DEBUG=false`,
  реальный `DATABASE_URL`, `CORS_ORIGINS` с доменом, `COOKIE_SECURE=true`,
  `COOKIE_SAMESITE`, `IP_HASH_SALT`, Telegram-токены; прогнать `alembic upgrade
  head` на staging Postgres; при старте в prod отказываться от `DEBUG=true`/
  `ALLOWED_HOSTS=*`/пустого БД-URL.
- **Сложность:** средняя.

#### P1-5 · P1 · низкая
**Расщепление env на build/runtime для API не задокументировано и не проверяется.**

- **Что найдено:** `NEXT_PUBLIC_API_BASE_URL` инлайнится в клиентский бандл при
  сборке, а `API_BASE_URL` читается сервером в runtime. Если задать env только при
  сборке и не передать в `next start`, получается гибрид: SSR-страницы и каталог
  работают на фикстурах, а клиентская проверка ответа и заявка идут в API.
- **Доказательство:**
  - `frontend/src/lib/api/server.ts:6` — `process.env.API_BASE_URL` в runtime.
  - `frontend/src/lib/api/config.ts:1-4` — `NEXT_PUBLIC_API_BASE_URL` (build-time).
  - Первый production-прогон (env только при сборке): каталог показал demo-задачи,
    `/zadachi/1042` → 200, хотя клиент ходил в API. Повторный прогон (env при
    сборке **и** запуске) → 17/17, каталог из API, `/zadachi/1042` → 404.
- **Последствия:** молчаливая несогласованность контента и canonical/ID;
  сложно диагностировать.
- **Исправление:** зафиксировать в deploy-документе «env нужны и на build, и на
  runtime»; добавить startup-guard/healthcheck, сверяющий доступность API;
  по возможности свести источники base-URL к одному.
- **Сложность:** низкая.

#### P1-6 · P1 · средняя
**Сборка frontend зависит от доступности API, если `API_BASE_URL` задан.**

- **Что найдено:** SSG-страницы (`/matematika`, `/informatika`, секции главной,
  `/articles`), `sitemap` и `generateStaticParams` вызывают `serverRequest` без
  fallback. При недоступном API во время сборки `serverRequest` бросает
  `ApiError`, и сборка падает.
- **Доказательство:**
  - `frontend/src/features/topics/components/subject-hub.tsx` — `getTasks`/
    `getArticlesBySubject` без try/catch.
  - `frontend/src/app/sitemap.ts:8` — `Promise.all([getTaskIds(), getArticles()])`.
  - `frontend/src/app/(public)/zadachi/[id]/page.tsx` / `articles/[slug]/page.tsx`
    — `generateStaticParams` через API.
  - `frontend/src/lib/api/server.ts` — бросает при сетевой ошибке.
- **Последствия:** деплой в неправильном порядке (frontend раньше API) ломает
  сборку; нет graceful degradation.
- **Исправление:** порядок деплоя «API → healthcheck → build frontend»;
  либо ISR/dynamic с fallback и понятной ошибкой; документировать.
- **Сложность:** средняя.

- **Что найдено:** `next.config.ts` не задаёт `Content-Security-Policy`,

  `X-Frame-Options`. Для CSP придётся учесть inline-скрипт инициализации темы и
  (опционально) Яндекс.Метрику.
- **Доказательство:** `frontend/next.config.ts` (только `poweredByHeader`,

- **Последствия:** ослабленная защита от XSS/clickjacking/MITM; замечания при
  security-ревью.
- **Исправление:** добавить заголовки (CSP с hash/nonce для inline-скрипта,
  HSTS только на HTTPS, `Referrer-Policy: strict-origin-when-cross-origin`).
- **Сложность:** средняя (CSP с inline-скриптом).
